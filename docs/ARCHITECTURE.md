# NexusCode Agent — Architecture

This document describes how NexusCode Agent is put together. It is intended for
contributors and for anyone who wants to extend the extension with a new
provider, tool, skill, or transport.

The high-level idea is simple: a VS Code extension hosts a webview UI on one
side and a tool-using LLM agent on the other. All persistent state lives on
the host; the webview is a thin React renderer that posts messages to the host
and receives state diffs back.

```
┌─────────────────────────────────────┐    postMessage     ┌───────────────────────────┐
│ Webview (React + Tailwind + Zustand)│ ─────────────────▶│ Extension host (Node, TS) │
│                                     │                    │                           │
│  • ChatView, DiffPanel, …           │ ◀─────────────────│  • runAgent (async gen)   │
│  • appStore (state, send())         │   state/replace    │  • providers, tools, MCP  │
│  • ApprovalDialog                   │   state/patch      │  • approval, security     │
│                                     │   task/*           │  • SettingsStore, etc.    │
└─────────────────────────────────────┘                    └───────────────────────────┘
```

---

## 1. Process model

NexusCode runs entirely inside the VS Code **extension host** process — no
secondary daemons, no language server. The webview is a Chromium iframe that
VS Code creates for the `nexuscode-sidebar` view; we lock it down with a strict
CSP and a per-load nonce (`webviewProvider.ts`).

Two communication channels:

1. **Webview ⇄ Host** — `vscode.postMessage` / `window.postMessage`. Every
   message is a discriminated union tagged by `type` (see `shared/protocol.ts`).
2. **Host ⇄ Provider** — plain `fetch` over HTTPS (or `child_process.spawn`
   for local providers like Ollama and MCP stdio servers). All requests honour
   `AbortSignal` for cancellation.

There are no shared-memory or worker threads. CPU-heavy work (line diffing,
secret scanning, ignore matching) is intentionally cheap and runs on the host
event loop.

## 3. Message protocol

`src/shared/protocol.ts` defines two discriminated unions:

| Direction | Categories |
|-----------|------------|
| `WebviewToHost` | lifecycle (`ui/ready`), task (`task/start`, `task/stop`, …), queue, approval, diff, persistence (`settings/save`, `providers/*`, `modes/*`, `skills/save`, `mcp/save`), checkpoint, command |
| `HostToWebview` | `state/replace`, `state/patch`, `task/message`, `task/update`, `task/streamDelta`, `task/toolStart`, `task/toolEnd`, `approval/request`, `diff/show`, `diff/clear`, `log`, `toast` |

Every host → webview update is either a full **`state/replace`** (used once at
mount and after major changes) or a **`state/patch`** (a shallow `Partial<AppState>`)
applied over the existing store. Streaming deltas during a task ride on
dedicated `task/*` messages so they don't trigger full re-renders.

The webview never holds long-lived references to disk paths, secrets, or
provider clients — those live exclusively on the host.

## 4. The agent loop (`core/agent/agentRunner.ts`)

The loop is implemented as an `async function*` that yields typed
`AgentEvent`s. The host adapts each event to the wire protocol:

```
runAgent(opts, deps, signal) yields:

  task_start               ─▶ host: task/update (status: running)
  text_delta               ─▶ host: task/streamDelta
  thinking                 ─▶ host: task/streamDelta (reasoning)
  tool_call_start          ─▶ host: task/toolStart
  tool_pending_approval    ─▶ host: approval/request  (awaits ApprovalGate)
  tool_call_end            ─▶ host: task/toolEnd
  diff                     ─▶ host: diff/show
  message_complete         ─▶ host: task/message
  usage                    ─▶ host: task/update
  task_end                 ─▶ host: task/update (terminal status)
  error                    ─▶ host: toast + task/update (status: failed)
```

Inside the loop, each turn:

1. **System prompt** is built by `promptBuilder.buildSystemPrompt`:
   - active mode's `systemPrompt`
   - matched skills (`instructions[]`, `workflow`, `outputFormat`,
     `safetyConstraints`)
   - `.nexusrules` content (via `rulesLoader.buildRulesSection`)
   - user `customInstructions` from settings
   - a one-paragraph summary of the available tools and their risk levels
2. **Tools available this turn** = `mode.allowedTools ∩ skill.allowedTools`.
   Skills can only narrow the tool set, never widen beyond the mode.
3. **`provider.stream(req)`** is called. The provider yields `ChatDelta`s
   (`text`, `reasoning`, `tool_call_start`, `tool_call_args`, `usage`).
   Tool-call deltas are accumulated by `id`.
4. **For each completed tool call**:
   - parse args, validate with the tool's **Zod** schema;
   - compute risk: `tool.assessRisk(args) ?? tool.riskLevel`;
   - run `evaluateApproval(policy, risk)`:
     - `auto-approve` → execute;
     - `auto-reject` → record a `[rejected by policy]` tool message and continue;
     - `ask` → push `ApprovalRequest` through `ApprovalGate.request`,
       await user decision in the webview, then execute or reject.
   - call `tool.execute(args, ctx)`; collect `ToolResult.diff` for the panel.
5. **Loop** until the model returns no tool calls (natural completion) or
   `MAX_ROUNDS = 8` is reached. Either way the loop ends with a `task_end`.

`AbortController` is propagated into every `fetch`, every `child_process`, and
every tool execute; `task/stop` aborts the controller and `ApprovalGate.cancelAll`
unblocks any pending approvals.

### Sub-modules

- **`taskManager.ts`** — in-memory store of `TaskRecord`s. Mutations call
  registered listeners which the host forwards as `task/update` patches.
  `recordToolCall` **merges** start/end events so `tool_call_end` does not
  overwrite the start-side metadata (name, riskLevel, args, startedAt).
- **`queueManager.ts`** — FIFO queue of pending user messages with statuses
  `queued`/`next`/`sent`/`cancelled`/`failed`. Supports edit, move
  (up/down/top), `sendNow` with a behavior flag (`interrupt-current`,
  `append-followup`, `replace-current`), pause/resume, clear. The highest-
  priority queued item is auto-tagged `next` for the UI.
- **`approvalGate.ts`** — pairs `request()` from the agent with `decide()`
  from the webview, via a Map keyed by `ApprovalRequest.id`. Stores a single
  promise resolver per request; `cancelAll` rejects all pending.

## 5. Provider system (`core/providers/`)

`LLMProvider` is the unified interface:

```ts
interface LLMProvider {
  readonly id, name, type, profile;
  listModels(opts): Promise<ModelInfo[]>;
  chat(req, opts):  Promise<ChatResponse>;
  stream(req, opts): AsyncIterable<ChatDelta>;
  // capability flags
  readonly supportsTools / Vision / ReasoningEffort / PromptCaching / JsonMode / ComputerUse;
}
```

Five concrete adapters:

| Adapter                       | Endpoint shape                                         | Streaming   | Tools |
|------------------------------ |--------------------------------------------------------|-------------|-------|
| `OpenAICompatibleProvider`    | `/v1/chat/completions` (Bearer or `api-key` header)    | SSE         | yes   |
| `AnthropicProvider`           | `/v1/messages` (content blocks, `tool_use`)            | SSE w/ events | yes |
| `GoogleGeminiProvider`        | `/v1beta/models/{m}:generateContent` (+ stream variant)| SSE         | yes   |
| `OllamaProvider`              | `/api/chat` + `/api/tags`                              | NDJSON      | yes   |
| `CustomHttpProvider`          | user-defined body template + response path             | SSE / NDJSON| limited |

The OpenAI-compatible adapter covers OpenAI, Groq, DeepSeek, xAI, Together,
Fireworks, Perplexity, Mistral, OpenRouter, LM Studio, LocalAI, Azure OpenAI,
Cohere, and HuggingFace.

**AWS Bedrock** has its own dedicated adapter (`bedrock.ts`) using
`aws-sigv4` request signing (`util/sigv4.ts`, pure-TS, no SDK) against the
unified [Converse / ConverseStream](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html)
APIs. Streaming uses Bedrock's binary `application/vnd.amazon.eventstream`
framing, parsed inline. Credentials are accepted as a JSON-encoded
`apiKey` (`{accessKeyId, secretAccessKey, sessionToken, region}`),
`profile.customParameters`, or `AWS_*` environment variables. The same
adapter works for Anthropic Claude, Meta Llama, Cohere Command, Mistral,
and Amazon Nova model families through Bedrock.

`providerRegistry.ts` holds the live `Map<id, LLMProvider>` and rebuilds an
adapter on profile mutations. It also exports `DEFAULT_PROFILES[]` — 13
out-of-the-box profile suggestions seeded into `globalState` on first run.

API keys never touch the profile object. They live in
`vscode.SecretStorage` via `ProviderSecretStore`, keyed by
`profile.apiKeySecretRef ?? profile.id`.

`util/sse.ts` is a small, dependency-free SSE parser used by every adapter
that streams.

## 6. Tools (`core/tools/`)

```
ToolDefinition<I> = {
  id, name, description,
  schema: ZodType<I>,         // validation
  parameters: JSONSchema,     // exposed to the LLM
  riskLevel: RiskLevel,       // safe | low | medium | high | critical
  assessRisk?: (args) => RiskLevel,  // per-call dynamic risk
  category: ToolCategory,
  producesDiff?: boolean,
  execute(args, ctx): Promise<ToolResult>,
}
```

24 built-in tools registered in `core/tools/builtin/index.ts`:

| Category    | Tools |
|-------------|-------|
| read        | `read_file`, `list_files`, `get_open_files`, `get_selection`, `get_symbols`, `get_terminal_output` |
| search      | `search_files`, `grep` |
| diagnostics | `get_diagnostics` |
| edit        | `write_file`, `edit_file`, `create_file`, `delete_file`, `rename_file` |
| shell       | `run_terminal_command` (dynamic risk via `assessCommandRisk`) |
| git         | `get_git_status`, `get_git_diff`, `create_git_branch`, `stage_files`, `commit_changes` |
| checkpoint  | `create_checkpoint`, `list_checkpoints`, `restore_checkpoint`, `rollback_checkpoint` |

Tool execution is sandboxed by `ToolContext`:

- `signal`: the agent's `AbortSignal` — every external call must propagate it.
- `ui`: VS Code helpers (showInfo/Warning/Error, getSelection, getOpenFiles,
  getDiagnostics, getSymbols, askUser). The host adapter
  (`core/tools/uiBridgeAdapter.ts`) wraps `vscode.window.activeTextEditor`,
  `vscode.languages.getDiagnostics`, and the
  `vscode.executeDocumentSymbolProvider` command.
- `security`: `isIgnored(path)`, `resolveWorkspacePath(path)` (traversal guard),
  `scanSecrets(content)` (returns redacted copy + matches).

The `get_terminal_output` tool reads from a small in-memory ring buffer in
`core/tools/builtin/terminalCapture.ts` that `run_terminal_command` writes to
after every invocation. This lets the agent inspect output from a previous
step without re-running the command (and without exposing the buffer to other
processes).

Edits never write to disk directly. `write_file`/`edit_file` build a
`DiffPreview` via `patchEngine.buildDiffPreview` and return it in
`ToolResult.diff`. The user accepts or rejects hunks in the diff panel.

## 7. Approval and risk policies (`core/approval/`)

The matrix:

| policy \\ risk | safe         | low          | medium       | high         | critical    |
|----------------|--------------|--------------|--------------|--------------|-------------|
| `manual`       | ask          | ask          | ask          | ask          | auto-reject |
| `balanced`     | auto-approve | ask          | ask          | ask          | auto-reject |
| `auto-safe`    | auto-approve | auto-approve | ask          | ask          | auto-reject |
| `full-auto`    | auto-approve | auto-approve | auto-approve | auto-approve | auto-reject |

Even `full-auto` blocks `critical`. There is no policy that silently runs
`rm -rf /`.

`assessCommandRisk(command)` scans a shell command against a regex table:

- `rm -r…`, `dd`, `mkfs`, `fdisk`, `parted`, `shutdown`, `reboot`, `curl … | sh`
  → `critical`
- `sudo`, `git push --force* main`, `git reset --hard`, `npm publish`,
  `docker rm/rmi/system prune`, destructive SQL (`DROP|TRUNCATE|DELETE`)
  → `high`
- read-only commands (`ls`, `pwd`, `cat`, `head`, `tail`, `grep`, `wc`,
  `git status|log|diff|branch|show`) → `safe`

Tools whose risk depends on args (notably `run_terminal_command`) provide an
`assessRisk` callback that the runner consults instead of the static
`riskLevel`.

## 8. Security (`core/security/`)

Three layers, applied at every boundary:

1. **`pathGuard.resolveWorkspacePath`** — refuses paths that escape the
   workspace root. Every tool that takes a `path` arg goes through this first.
2. **`IgnoreMatcher`** — gitignore-style matcher with `*`, `**`, `?`, `!`,
   anchored `/`, dir-only trailing `/`. Loads `SAFE_DEFAULT_IGNORES`,
   `.nexusignore`, and `.gitignore`. The matcher is consulted before any
   `read_file`, `list_files`, `search_files`, `grep`, or context-ref expansion.
3. **`scanSecrets`** — regex-based redactor for OpenAI, Anthropic, GitHub
   PAT/OAuth/App, Google API, AWS, Slack, Stripe, Bearer, JWT, PEM private
   keys, Azure storage, Discord-bot, Telegram-bot. Applied to file contents
   before they are sent back to the LLM as a tool result, and to `stdout` /
   `stderr` from `run_terminal_command`.

See [`SECURITY.md`](./SECURITY.md) for the full security model.

## 9. Context refs and token budget (`core/context/`)

`@kind:value` references inside chat messages are parsed by `contextRef.ts`:

| Ref          | Resolves to                                    |
|--------------|------------------------------------------------|
| `@file:p`    | full file content (≤ 64 KB, secret-redacted)   |
| `@folder:p`  | recursive listing (≤ 50 entries)               |
| `@symbol:s`  | `vscode.workspace.getSymbols` matches          |
| `@terminal`  | last terminal output                           |
| `@problems`  | workspace diagnostics (≤ 100)                  |
| `@gitdiff[:ref]` | `git diff [ref]`                           |
| `@openfiles` | currently-open editors                         |

Resolved `ContextChunk`s are packed into a token budget (default 8 000 / turn)
by `tokenBudget.packBudget`, a greedy priority-based packer. The order in the
final prompt preserves document order, not priority order.

## 10. Skills (`core/skills/`)

A skill is a curated procedure. `SkillDefinition` carries:

- `triggers[]` — substrings checked against the user message;
- `instructions[]`, `workflow[]`, `outputFormat`, `safetyConstraints`;
- `allowedTools[]` — intersected with the active mode's allow list.

`SkillRegistry.match(message)` returns every skill whose triggers fire. The
prompt builder injects all matched skills into the system prompt.

Project skills are loaded from `.nexus/skills/**/*.skill.json` by
`skillLoader.ts`. Bad files report into `errors[]` and are logged; one broken
file does not disable the rest.

20 built-in skills cover the high-leverage workflows (Add Feature, Fix Bug,
Refactor, Explain Code, Write Tests, Review PR, Optimize Performance,
Documentation, API Design, Security Audit, Dependency Audit, Git Commit,
Create Branch, DevOps & CI, DB Migration, Frontend Component, API Endpoint,
Microbenchmark, Localize, Notebook Cleanup).

## 11. MCP (`core/mcp/`)

Three transports are supported, all implementing the same `McpClient`
interface (`start`, `listTools`, `callTool`, `stop`, `isRunning`,
`uptimeMs`):

- **stdio** (`McpStdioClient`) — spawns a child process and speaks
  **Content-Length-framed JSON-RPC 2.0** over its stdio (the same framing
  as LSP, mandated by the MCP spec for stdio transport).
- **Streamable HTTP** (`McpHttpClient` with `transport: "http"`) — single
  POST endpoint per MCP spec **2025-03-26**. Each client request is a POST
  whose response can be either `application/json` or `text/event-stream`
  (SSE) carrying the JSON-RPC reply plus optional server-initiated
  notifications. The `Mcp-Session-Id` response header is captured and
  echoed on subsequent requests.
- **HTTP+SSE** (`McpHttpClient` with `transport: "sse"`) — legacy
  transport from MCP spec **2024-11-05**. The client opens a long-lived
  `GET` for SSE; the first `event: endpoint` announces the POST URL for
  client-to-server messages; subsequent `event: message` SSE frames
  deliver server-to-client JSON-RPC replies.

All clients implement `initialize` → `notifications/initialized`,
`tools/list`, and `tools/call`, with request correlation by `id`,
configurable timeouts, and abort-aware `stop()`.

`McpManager` keeps a `Map<id, McpClient>` and aggregates discovered
tools into a single `McpToolDescriptor[]`. Tool aggregation triggers a
`state/patch { mcpTools }` so the UI updates live. The transport is
selected from `McpServerConfig.type` (`"stdio" | "http" | "sse"`).

HTTP / SSE transports are not yet implemented — `mcpManager.startServer`
emits an `error` status with the message `transport "<x>" not yet implemented`.

## 12. Checkpoints (`core/checkpoint/`)

`CheckpointManager` saves per-task file snapshots to disk under
`<extensionGlobalStorage>/checkpoints/<id>/`. Each checkpoint has:

- a `meta.json` (id, taskId, label, createdAt, file list),
- one blob per snapshot file (filename sanitised to `[a-zA-Z0-9._-]`).

`init()` rebuilds the in-memory index by scanning `meta.json` files. The
manager trims oldest checkpoints when the count exceeds
`nexus.checkpoints.maxCount` (default 50).

## 14. State management (host & webview)

- **Host state** — held in plain TS objects: `SettingsStore`,
  `ProviderProfileStore`, `ProviderSecretStore`, `QueueManager`,
  `TaskManager`, `SkillRegistry`, `McpManager`, `CheckpointManager`. None of
  them are reactive; mutations explicitly call `post()` to send a `state/patch`
  to the webview.
- **Webview state** — Zustand store (`stores/appStore.ts`) holds the latest
  `AppState` plus UI-only fields (`activeView`, `toasts[]`). On `ui/ready` the
  host sends a `state/replace`; thereafter every change is a `state/patch`.

Settings are persisted via `vscode.workspace.getConfiguration("nexus")` and
written at `ConfigurationTarget.Global`. Profiles, recent tasks, and queue
state live in `globalState`. API keys live in `secretStorage`.

## 17. Extension activation flow

`extension.ts → activate(context)`:

1. Build stores: `SettingsStore`, `ProviderProfileStore` (`globalState`),
   `ProviderSecretStore` (`secretStorage`), `ProviderRegistry`.
2. Build `ToolRegistry`, register the 24 built-in tools.
3. Build `SkillRegistry`, register the 20 built-in skills, then load any
   project skills from `<workspace>/.nexus/skills`.
4. Build `McpManager` and wire its `tools`/`status` listeners to webview
   patches.
5. Build `CheckpointManager` rooted at `globalStorageUri/checkpoints/`.
6. Build `QueueManager`, `TaskManager`, `ApprovalGate`. Wire their listeners
   to `task/update` and `approval/request` messages.
7. Register the `NexusWebviewProvider` and the `nexus.*` commands.
8. Register `onDidChangeConfiguration("nexus")` to push settings patches.
9. Add a dispose hook that calls `mcpManager.stopAll()`.

No work happens until the user interacts with the webview.

## 18. Extension points

| What you want to add        | Where                                                      |
|-----------------------------|------------------------------------------------------------|
| New LLM provider adapter    | `core/providers/<name>.ts` + entry in `providerRegistry`   |
| New built-in tool           | `core/tools/builtin/<x>.ts` + register in `builtin/index`  |
| Custom skill (project)      | `<workspace>/.nexus/skills/<id>.skill.json`                |
| Custom mode (project)       | `<workspace>/.nexus/modes/<id>.json`                       |
| New context ref kind        | extend `ContextRefKind` and `resolveRef` in `contextBuilder` |
| New approval policy         | extend the `ApprovalPolicy` union and the matrix in `evaluateApproval` |
| New MCP transport           | implement the `McpClient` interface in a sibling to `McpStdioClient` / `McpHttpClient` and dispatch from `McpManager.createClient` |

For provider adapters, the bar is the `LLMProvider` interface plus capability
flags. For tools, the bar is a Zod schema + `execute` that propagates
`ctx.signal` and uses `ctx.security` for any I/O.
